<a id="agent-onboarding"></a>
# 代理入门

仅凭仓库和用户目标任务，代理应能理解 Harneloop。第一步不是编写验证器或假定已有测试命令，而是收集足够上下文来创建基线尝试。

面向人的引导式设置：

```powershell
harneloop setup
```

面向代理的检查清单：

```powershell
harneloop onboard
```

或在持久安装工具前，从仓库克隆运行：

```powershell
uv run harneloop onboard
```

机器可读输出：

```powershell
harneloop onboard --format json
```

旧版 Harneloop 创建的单元，请运行一次 `harneloop upgrade-unit <unit>`。它补齐框架协议文件，不替换已有 harness 材料。

<a id="minimal-user-questions"></a>
## 最少用户问题

将这些作为上下文字段，而非必答问卷。代理可先创建临时单元、检查工作区，再只询问仍重要的问题：

1. 这个 harness 应帮助代理在哪方面提升？
2. harness 将用于哪里，例如编码代理流程、应用代理、研究或内部自动化？
3. 成功标准应如何处理？
4. 如何验证结果？
5. 测试环境已存在、部分存在、需要构建，还是尚不清楚？

不要将入门变成冗长表单。成功标准与产物选择是引导式选项，不要求用户具备专业知识。检查后运行 `harneloop intake status <unit>`，将重要上下文分类为已确认、已委托、推断、未知或不适用。不要悄悄把推断变成已确认事实。

首次真实运行前，解决相关字段并用 `harneloop intake acknowledge` 记录用户明确确认或委托。如果缺失的参考资料、目标项目、凭证或判断会实质改变测试，直接请求或进入等待状态，不要只在设置结束后提及。

Harneloop 记录环境映射，不会自行发现测试端点、MCP 工具、运行命令、截图位置、渲染输出或产物路径。入门代理必须检查实际项目与环境，确定产物生成方式，并将映射写入 harness。

每个新单元都有 `operational-map.md`。用它记录当前导航：改进目标、交互的系统和工具、有用产物与证据、通常运行及重置方式、已知约束、脆弱点、未决问题、待复查假设及既有运行或证据位置。工作流、证据需求、环境假设或自动化策略变化时更新。

地图是上下文与导航，不是固定程序。代理仍应从任务出发推理、检查可用证据，并为当前尝试选择适当测试或评估策略。

<a id="capability-gaps"></a>
## 能力缺口

不要假定每个操作代理都具备 Codex 级能力。定制 Hermes、OpenClaw、应用代理或受限自动化工作进程可能没有终端、文件系统、浏览器、包管理器、MCP 服务器、视觉检查、数据库或其他构建单元所需能力。

区分两层：

- 操作代理能力：当前代理构建单元时实际可用的能力。
- 单元或目标代理工具：单元内设计的工具，或通过环境契约提供给目标代理的工具。

操作代理缺少有用能力时，在 `operational-map.md` 记录：缺少什么、为什么重要、哪些工具或依赖能帮助、引入的风险/费用/认证/安全变化，以及用户拒绝时的替代方案。

环境允许时，可安装、启用或构建低风险本地能力。较大依赖、凭证、付费 API、用户账户、外部访问、网络扩展或安全影响变更应先提议。

增加能力应以已观察瓶颈、失败尝试、缺失产物或明确预期改进为依据，不要猜测性添加。

<a id="reuse-existing-work"></a>
## 复用现有工作

目标是最佳已验证 harness，而非从零实现。构建缺失能力前，检查现有项目工具、开源库、代理技能、MCP 服务器、验证器、数据集、示例、文档、研究和可复用材料。若可能改善结果或减少无谓工作，代理可安装、适配、组合或借鉴合适成果。

不要盲目复用。记录来源、相关版本或修订、用途、许可或署名义务、兼容性假设及有帮助的证据。信任前审查第三方可执行材料。引入凭证、付费服务、外部访问、大量下载、限制性许可、安全敏感执行或重大环境变化时先询问。现有方案不合适时，先记录原因再构建替代。

成功策略建议选项：

- 让代理提出成功标准。
- 我知道准确的成功结果。
- 首次基线尝试后再决定。

验证建议选项：

- 最佳验证质量。
- 视觉或产物优先验证。
- 平衡验证。
- 资源高效验证。
- 让代理逐任务决定。

可选追问：

- harness 是否须遵守约束、受保护区域、人工审查点或费用/时间限制？

<a id="how-answers-map-into-harneloop"></a>
## 回答如何映射到 Harneloop

- 目标、成功策略、验证偏好和建议产物形成目标简报：`harneloop target set`。
- 单元当前工作地图记录并修订于 `operational-map.md`。
- 现有命令、MCP 服务器、手动步骤或自定义工具形成环境契约：`harneloop environment connect`。
- 首个真实工作流形成尝试计划：`harneloop attempt plan`。
- 生成输出成为运行产物：`harneloop run start`、`harneloop artifact add`、`harneloop run finish`。
- 使用 `harneloop attempt conclude` 记录结果质量与下一生命周期决定。
- harness 变更成为候选，提升前需要证据。
- 使用 `harneloop settings` 管理用户默认值。
- 用 `harneloop units` 列出或注册本地单元。注册后，可在任意目录的单元命令中使用其 ID 或名称。

<a id="important-behavior"></a>
## 重要行为

Harneloop 不要求每项任务有直接测试命令。Blender MCP 或代理控制的 SVG 渲染等工具驱动环境，应在环境契约中声明工具与产物。代理再编写如何使用工具、产生产物、检查产物并将观察转为证据的尝试计划。

代理应争取重复测试和改进，而无需用户手动重启应用、重装插件、重置服务或收集文件。环境自动化合理时，实现或记录；若有风险、不明确、过于昂贵或耗时，先询问。

必要产物或人工判断延迟时，使用 `harneloop state wait`。单元似乎达到能力极限时，使用 `harneloop state stop` 并说明具体原因与下一步。

结束运行仅记录执行状态，不证明结果质量。检查产物，并为每次尝试明确决定：接受当前 harness、创建候选、按修正计划重跑、请求缺失输入或停止。首个好结果可直接接受，无需候选。缺少预期证据不能支持无保留通过。

进入或恢复单元工作时，运行 `harneloop brief <unit>`。生成简报仅限该 harness 单元，不影响同一代理会话中的无关工作。

<a id="candidate-batching-and-parallel-work"></a>
## 候选批次与并行工作

候选代表一个连贯变更假设，不对应每次编辑或提交。需一起判断的相关环境设置、工具、指令或验证器变更应组成批次。无关问题分开候选，多个候选可同时开放。

按影响分类每个候选：

- `target_harness`：改变目标代理收到的内容或能力；
- `evaluation`：改变输出的观察或判断方式；
- `infrastructure`：改变设置、执行、重置或产物收集；
- `mixed`：仅用于无法有意义地分开的情况。

按失败风险选择验证：

- `structural`：解析、schema、静态检查及元数据完整性；
- `targeted`：针对工具、评估器或基础设施路径的冒烟测试；
- `representative`：行为变更的真实任务尝试和相关回归；
- `full`：高影响变更和发布检查点的广泛套件。

不要为每次设置编辑重跑完整基准。候选先积累至连贯，标记 `ready`，再按声明层级收集证据。尽可能将目标 harness 与评估候选分开，避免修改过的评估器成为修改过的 harness 的唯一裁判。

已提升 harness 版本保持线性。一个候选提升后，其他基于旧版本的候选被标记 `needs_rebase`。协调并变基，然后针对新基线收集新证据；旧证据仍作为来源记录保留。
