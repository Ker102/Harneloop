<a id="product-principles"></a>
# 产品原则

Harneloop 是选定的产品名称。架构保持独立，不依赖任何单一基准或任务类别。

<a id="what-this-is"></a>
## 它是什么

Harneloop 是供代理构建和改进自身或其他目标代理周围 harness 的框架。

框架应帮助代理：

- 执行任务尝试；
- 检查真实产物；
- 将失败追溯到运行；
- 维护单元内的操作地图，记录工作流、证据、环境假设和未决问题；
- 将操作代理的能力缺口与单元或目标代理工具分开识别；
- 研究并复用合适的工具、技能、库、数据集、示例和既有工作；
- 提出候选 harness 补丁；
- 测试候选补丁；
- 仅提升有证据支持的改进；
- 打包可移植的 harness 单元。

<a id="what-this-is-not"></a>
## 它不是什么

Harneloop 不是：

- 通用评估仪表板；
- 固定的代理图框架；
- Blender 专用系统；
- 模型训练或微调系统；
- 没有生命周期的松散提示词文件夹。

<a id="core-design-tension"></a>
## 核心设计张力

系统面向生成式 AI 模型，因此必须为推理和探索留出空间。同时，框架必须保护生命周期完整性。

规则：

> 代理可以在候选内自由探索。引擎控制提升。

`operational-map.md` 用于保存代理对 harness 单元的当前理解，而不将这种理解固化为脚本。代理应借助它定位工作、随证据变化更新它，并仍然根据当前任务和产物进行推理。

框架不应假定构建 harness 单元的代理无所不能。应识别操作代理缺失的能力，以证据或明确预期改进来证明需求，并在添加工具、依赖、凭证、付费服务或更广泛外部访问前遵守相应权限边界。

Harneloop 优化的是经过验证的最佳任务表现，而不是从零重建每种能力。操作代理应检查现有方案，并可在有利于 harness 时采用、适配、组合或借鉴它们。复用必须可审查：记录用了什么及原因，验证兼容性与实测价值，遵守许可和署名要求，并对安全、凭证、外部访问、费用或重大基础设施变更采用通常的权限门槛。
