<a id="runtime-layers"></a>
# ランタイムの層

<a id="current-decision"></a>
## 現在の方針

最初の参照実装には Python を使います。

将来 Harneloop に保護されたネイティブランタイムが必要になった場合は、Go より Rust を優先します。

<a id="why-rust-later"></a>
## 将来 Rust を使う理由

ネイティブ層は、フレームワークが次について、より強いローカル保証を必要とする場合にのみ設けるべきです：

- ライフサイクルの整合性；
- 保護された状態の境界；
- バージョンスナップショット；
- ロールバック；
- 内容アドレス方式のストレージ；
- 成果物のパッケージ化；
- ファイル監視；
- サブプロセスの監視；
- デスクトップ向けパッケージ化。

この製品の形態では、保護されたカーネルの役割に Go より Rust が適しています。

<a id="agent-boundary"></a>
## エージェントとの境界

Rust を、エージェントが自由にハーネスを設計するワークスペースにしてはいけません。

エージェントは引き続き次を通じて作業します：

- Markdown の指示；
- YAML と JSON のマニフェスト；
- スキーマ；
- 候補ディレクトリ；
- CLI コマンド；
- 成果物の契約。

ルールは変わりません：

> エージェントは候補内で自由に探索できます。昇格はエンジンが制御します。

<a id="where-go-could-still-fit"></a>
## Go が適する可能性のある領域

Harneloop がその方向に発展する場合、Go は将来のホスト型サービス、リモートワーカーの調整、レジストリ基盤に引き続き適した候補です。
