<a id="agent-onboarding"></a>
# エージェントの導入

リポジトリとユーザーの対象タスクだけで Harneloop を理解できるようにしてください。最初の手順はバリデーターを書くことでもテストコマンドの存在を想定することでもなく、ベースライン試行を作るための十分な情報収集です。

人向けのガイド付きセットアップ：

```powershell
harneloop setup
```

エージェント向けチェックリスト：

```powershell
harneloop onboard
```

またはツールを恒久インストールする前にクローンから：

```powershell
uv run harneloop onboard
```

機械可読出力：

```powershell
harneloop onboard --format json
```

旧バージョンで作成したユニットには `harneloop upgrade-unit <unit>` を一度実行します。既存のハーネス素材を置き換えず、足りないプロトコルファイルを追加します。

<a id="minimal-user-questions"></a>
## 最小限のユーザー質問

必須の質問票ではなく、コンテキストの項目として使います。先に暫定ユニットを作って環境を調べ、その後に残る重要な疑問だけ尋ねられます：

1. このハーネスでエージェントの何を改善するか？
2. コーディングエージェント、アプリエージェント、研究、内部自動化など、どこで使うか？
3. 成功基準をどう扱うか？
4. 結果をどう検証するか？
5. テスト環境は存在するか、一部存在するか、構築が必要か、まだ不明か？

導入を長いフォームにしないでください。成功基準と成果物は案内付きの選択であり、ユーザーの専門知識を要求しません。調査後に `harneloop intake status <unit>` を実行し、重要な情報を確認済み、委任済み、推論、未知、不適用に分類します。推論を黙って確認済み事実にしないでください。

初回の実行前に関連項目を解決し、`harneloop intake acknowledge` で明示的な確認または委任を記録します。参照資料、対象プロジェクト、認証情報、判断の不足がテストを変え得るなら、設定後に述べるだけでなく、直接要求するか待機してください。

Harneloop は環境対応を記録しますが、テスト先、MCP ツール、実行コマンド、スクリーンショットの場所、レンダリング、成果物パスは自動発見しません。導入エージェントが実際のプロジェクト・環境を調べ、成果物の作成方法を特定して対応を記録します。

新ユニットには `operational-map.md` があります。改善対象、関係するシステムとツール、有用な成果物・証拠、通常の実行とリセット、制約、脆弱箇所、未解決の疑問、再確認する前提、過去の実行・証拠の場所を示す現状案内として使います。作業、証拠の要件、環境前提、自動化戦略が変わったら更新します。

マップはコンテキストと案内であり固定手順ではありません。エージェントはタスクをもとに推論し、証拠を確認して、現在の試行に適したテスト・評価戦略を選びます。

<a id="capability-gaps"></a>
## 能力の不足

すべての操作エージェントに Codex 並みの能力があると想定しないでください。独自 Hermes、OpenClaw、アプリエージェント、制限付き自動化ワーカーには端末、ファイル、ブラウザ、パッケージ管理、MCP、視覚確認、DB など、ユニット構築に必要な機能がない場合があります。

2 つの層を分けます：

- 操作エージェントの能力：ユニット構築時に実際に使えるもの。
- ユニット・対象エージェントのツール：ユニットに設計されたものや環境契約で対象エージェントに提供されるもの。

有用な能力が不足したら `operational-map.md` に、何が不足するか、重要な理由、役立つツール・依存関係、リスク・費用・認証・安全への影響、拒否された場合の代替を記録します。

環境が許せば低リスクのローカル能力をインストール、有効化、構築できます。大きな依存関係、認証情報、有料 API、ユーザー所有アカウント、外部アクセス、ネットワーク拡張、セキュリティ変更は先に提案します。

能力追加は、観察したボトルネック、失敗試行、欠落成果物、明確な改善見込みで正当化し、思いつきで追加しないでください。

<a id="reuse-existing-work"></a>
## 既存成果の再利用

目標は最良の検証済みハーネスで、ゼロからの実装ではありません。不足能力を作る前に、既存ツール、OSS ライブラリ、スキル、MCP、バリデーター、データセット、例、文書、研究、再利用素材を調べます。結果改善や不要な労力削減につながるなら、適切な成果を導入、適応、組み合わせ、学習できます。

盲目的に再利用しないでください。出典、関連版・リビジョン、用途、ライセンス・帰属義務、互換性の前提、効果の証拠を記録します。第三者実行物は信頼する前に確認します。認証情報、有料サービス、外部アクセス、大量ダウンロード、制約的ライセンス、危険な実行、重要な環境変更には先に確認します。既存案が不適切なら、代替を作る前に理由を記録します。

成功についての回答例：

- エージェントに成功基準を提案させる。
- 成功した結果を正確に知っている。
- 初回ベースライン後に決める。

検証についての回答例：

- 最良の検証品質。
- 視覚または成果物優先の検証。
- バランスの取れた検証。
- 資源効率の高い検証。
- タスクごとにエージェントが判断する。

任意の追加質問：

- 制約、保護領域、人のレビュー箇所、費用・時間制限はあるか？

<a id="how-answers-map-into-harneloop"></a>
## 回答と Harneloop の対応

- 目標、成功戦略、検証の優先、推奨成果物は対象ブリーフになります：`harneloop target set`。
- 現在の作業マップを `operational-map.md` に記録・更新します。
- 既存コマンド、MCP、手動手順、独自ツールは環境契約になります：`harneloop environment connect`。
- 最初の実ワークフローを試行計画にします：`harneloop attempt plan`。
- 出力を実行成果物にします：`harneloop run start`、`harneloop artifact add`、`harneloop run finish`。
- 結果の品質と次の判断を `harneloop attempt conclude` で記録します。
- ハーネス変更は候補となり、昇格前に証拠が必要です。
- ユーザーの既定値は `harneloop settings` で管理します。
- `harneloop units` でローカルユニットを一覧・登録できます。登録後は任意ディレクトリのユニット用コマンドで ID や名前を使えます。

<a id="important-behavior"></a>
## 重要な動作

すべてのタスクに直接テストコマンドは不要です。Blender MCP やエージェントの SVG レンダリングなどでは、環境契約にツールと成果物を宣言します。その使用、成果物の生成と確認、観察から証拠への変換を試行計画にします。

アプリの手動再起動、アドオン再導入、サービスのリセット、ファイル収集をユーザーに要求せず、繰り返し検証できることを目指します。妥当なら自動化を実装・記録し、危険、不明、高額、長時間なら先に確認します。

必要な成果物や人の判断が遅れたら `harneloop state wait` を使います。能力限界に達したようなら、理由と次の行動を示して `harneloop state stop` を使います。

実行終了は状態の記録で、品質証明ではありません。成果物を確認し、現状受け入れ、候補作成、修正計画で再実行、入力要求、停止のどれかを明示します。初回の良好な結果は候補なしで受け入れられます。期待する証拠が欠けたまま無条件合格にはできません。

ユニットの開始・再開時には `harneloop brief <unit>` を実行します。生成ブリーフはそのユニットに限定され、同じセッションの無関係な作業には影響しません。

<a id="candidate-batching-and-parallel-work"></a>
## 候補のまとめ方と並行作業

候補は一貫した変更仮説であり、編集・コミットごとではありません。同時に評価する関連設定、ツール、指示、バリデーターをまとめ、無関係な問題は別候補にします。複数を開いたままにできます。

各候補を影響で分類します：

- `target_harness`：対象エージェントに渡す内容や能力を変更；
- `evaluation`：出力の観察・評価方法を変更；
- `infrastructure`：設定、実行、リセット、成果物収集を変更；
- `mixed`：意味を損なわずに分離できない場合だけ使用。

失敗リスクに応じて検証を選びます：

- `structural`：解析、スキーマ、静的検査、メタデータ整合性；
- `targeted`：1 つのツール、評価器、インフラ経路のスモークテスト；
- `representative`：動作変更の実タスク試行と関連回帰；
- `full`：大きな影響の変更やリリース確認での広いテスト。

設定変更ごとにベンチマーク全体を回さないでください。候補をまとめて `ready` にし、宣言レベルで証拠を集めます。対象ハーネスと評価候補を可能なら分け、変更した評価器だけで変更ハーネスを判断しないでください。

昇格済み版は直線的です。1 つが昇格すると旧ベースを共有する他候補は `needs_rebase` になります。整合を取り、リベースし、新しいベースで証拠を集めます。古い証拠は来歴として残ります。
